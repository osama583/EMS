# Database

PostgreSQL 17 on Supabase, reached through the session pooler (port 5432) so
prepared statements work.

## Migrations

```bash
python -m migrations.run --status   # what would run
python -m migrations.run            # apply pending
python -m migrations.run --reset    # drop and recreate (development only)
```

| File | Contents |
|---|---|
| `001_initial_schema.sql` | `ems_database_schema.sql` **verbatim** — 59 tables |
| `002_performance_indexes.sql` | 26 secondary indexes for the API's hot paths |
| `003_grant_id_identity.sql` | Makes `nav_page_grants.grant_id` self-assigning |

001 is copied unmodified from `fyp-ui/docs/system-logic/`, so any drift between
the source of truth and what is deployed shows up as a plain `diff`. Corrections
belong in a new numbered migration, never in an edit to 001.

Each file runs in its own transaction and is recorded in `schema_migrations` by
filename and SHA-256. Re-running is a no-op. A file edited after being applied is
reported rather than silently skipped — that is how two environments quietly
diverge.

## Documented deviations

The brief allows schema changes only where necessary, documented clearly. There
is exactly one.

### `nav_page_grants.grant_id` (migration 003)

The source schema declares:

```sql
grant_id INTEGER PRIMARY KEY
```

with no `DEFAULT` and no sequence — the only surrogate key in the schema that is
not `BIGSERIAL`. Almost certainly because the JSON mock assigned ids in
application code.

Left alone, every insert must compute `max(grant_id) + 1` and then race any
concurrent insert for the same value. The Page Visibility screen creates these
rows interactively, so the race is reachable in ordinary use.

003 adds `GENERATED BY DEFAULT AS IDENTITY`. **The column name and type are
unchanged**; only the default is added, so existing rows and every query against
them keep working.

## Constraints worth knowing

**`nav_page_grants` is `UNIQUE (page_code, grant_type)`** — a page holds at most
one grant row per type. Where the seed catalogue naturally produces two of the
same type (Inbox: the unit roles, plus Cafeteria Manager), they merge into one
row's role and unit sets.

Merging turns two cross-products into one larger one, which nominally widens
access: the merged Inbox row allows "student in a cafeteria unit" and
"cafeteria-manager in a school". Neither is reachable — `role_unit` governs which
(role, unit) pairs may be assigned at all, and neither pairing is linked there,
so no user can hold one. `PUT /admin/nav-pages/{code}/grants` rejects duplicate
types with an explanatory message rather than a constraint violation.

**Partial unique indexes** carry two rules the API also checks for better
messages:

```sql
uq_event_registration_active  ON (request_id, user_id) WHERE status <> 'cancelled'
uq_club_join_request_pending  ON (club_id, requester_user_id) WHERE status = 'pending'
```

Both allow a second attempt after cancelling or being rejected, while blocking
two live ones. The database is the real guard; the API check exists only to
return a friendlier error.

**`chk_task_routing`** makes `assigned_unit_code` and `assigned_role` mutually
exclusive. The five Service-department requirements route by unit; `fmb` and
`cfo` route by flat role.

## Snapshot columns

Several tables freeze catalogue text at write time: `request_categories.category_name`,
`request.event_format_snapshot`, `request_mineral_water.option_label`,
`request_fmb_selection.menu_item_label`.

This is deliberate denormalisation. Renaming or retiring an option must not
rewrite what a submitted proposal said at the time. It also means deleting an
option is safe — soft-delete stops new selections without touching history.

## Co-owners are snapshots too

`co_owners` has **no `user_id`**. It stores `staff_id` (nullable — null when the
co-owner was typed in rather than picked from the directory) plus a name and
email snapshot. Ownership checks therefore match on `staff_id` **or** the
lowercased email:

```sql
LEFT JOIN staff s ON s.staff_id = c.staff_id
WHERE s.user_id = %s OR lower(trim(c.staff_email)) = lower(%s)
```

Both paths are indexed. This caught out migration 002's first draft, which
assumed a `user_id` column existed.

## Reserved words

`event_schedule.date` and `brief_agenda.time` collide with type names and must
be double-quoted in SQL. Unquoted references parse ambiguously inside aggregates.

## Cafeterias are units

There is no `cafeteria` table. A cafeteria is a `unit` row with the code prefix
`cafeteria__`, and its staffing is ordinary `user_unit_roles` rows
(`cafeteria-manager` / `cafeteria-staff`). "Which cafeterias exist" is a prefix
query — note `_` is a LIKE wildcard and must be escaped:

```sql
WHERE code LIKE 'cafeteria!_!_%' ESCAPE '!'
```

Passwords are bcrypt-hashed. The plaintext is printed once at the end and is not

`--reset` truncates seedable tables but **refuses if any proposal exists** —
those are real work, and cascading through them would destroy it silently.

## Connection pooling

`ThreadedConnectionPool`, 1–10 connections, with TCP keepalives. Supabase's
pooler terminates idle connections; without keepalives a request eventually gets
handed a dead socket.

Reads use `read_cursor()`, which rolls back on exit — a read still opens a
transaction in Postgres, and skipping this leaves pooled connections sitting
"idle in transaction". Writes use `transaction()`, which commits on success and
rolls back on any exception, so a partially applied workflow transition cannot
be left behind.
