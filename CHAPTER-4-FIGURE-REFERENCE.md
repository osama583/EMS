## 1. The system in brief

APU EMS is a university event management platform. An **Angular 21** single-page
client talks to a **Flask** REST API over **Supabase PostgreSQL**. The backend owns
the entire workflow: the acting user always comes from the JWT rather than a request
field, list endpoints are scoped in SQL to what the caller may see, and every stage
transition is recorded in `workflow_history` inside the same transaction as the
change itself.

The core journey is an **event proposal**. A staff member or student drafts one
through a six-step form, submits it, and it moves through a routed approval chain —
Head of School/Head of Department, then Food & Beverage and the CFO where thresholds
demand it, then the operational departments (Logistics, A/V, Transport, Photography,
Student Services) that must fulfil the individual requirements. Approved proposals
become published events that the public can discover and register for. Alongside
this sit a clubs module, a cafeteria ordering module, role-specific dashboards, a
system administration area, and an AI assistant that answers questions in natural
language over the data the asker is allowed to see.

Scale, useful when describing the design: **68 tables, 471 columns, 111 foreign
keys, 33 ordered migrations**; roughly **187 demo accounts** across 15 role types;
**140 CSS design tokens**; **50+ shared UI components**.

## 7. Caveats to respect when writing

These are real and were verified against the live system. Do not write around them
as if they were not there.

1. **4.5.06 Event Details Modal does not show a modal.** The events list endpoint
   never returns a `clubs` field, but the event card and the details modal templates
   both read `clubs.length`. Every card throws, so the modal renders empty and the
   card loses its registered-count line. The figure therefore shows the explore grid.
   Either omit the figure, or cite it honestly in a limitations paragraph.

2. **4.5.62 and 4.5.63 show empty states.** No registration anywhere in the database
   is in `pending` status, so there is genuinely nothing awaiting approval. The empty
   state is correct application behaviour, not a capture failure — caption it that
   way, or leave both out.

3. **The events and My Events area was mid-refactor when these were captured.** On My
   Events the filter reads "0 events found" while the grid below shows saved event
   cards; the count is out of sync with the results. If that has since been fixed,
   re-capture 4.5.12 to 4.5.15 and 4.5.20 before submitting.

4. **Two figures are the same underlying screen at different scopes** — 4.5.30
   (reviewer) and 4.5.31 (department) are both the proposal review page. Say so
   rather than presenting them as unrelated screens; the contrast *is* the point.

5. **Prefer desktop images as the primary figure.** Use the mobile pair only where
   the text discusses responsive design, otherwise the chapter doubles in length for
   little gain.

## 8. Regenerating any of this

The capture harness lives in `ui png/_capture/` and runs against the live
application with both servers up (`backend` on `:5000`, `fyp-ui` on `:4200`):

```bash
cd "ui png/_capture" && npm install
node preflight.mjs                  # which routes each demo account can actually open
node capture.mjs                    # all 80 pages; --group A or --only 4.5.01 to narrow
node build_design_figures.mjs       # the section 4.4 artefacts
python build_code_figures.py && node shoot_code.mjs   # the section 4.6 listings
node build_index.mjs                # regenerates ui png/FIGURE INDEX.md
```

`ui png/FIGURE INDEX.md` is a shorter machine-generated companion to this file: the
same figure list with the account and route for each, produced directly from the
shot definitions so it cannot drift.
